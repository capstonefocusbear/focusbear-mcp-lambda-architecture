# Durable Auth0 revocation queue

Disconnect commits a local disabled connection before returning. Every subsequent MCP request checks that row; queued Auth0 work cannot grant access. No background job claims remote revocation has happened. A trusted administrator must drain this durable queue using the following workflow.

1. Set `FOCUSBEAR_API_URL` and `FOCUSBEAR_ADMIN_TOKEN` (a normal Focus Bear API token for an administrator) in the operator environment. Run `node apps/api-server/scripts/mcp-revocations.mjs list`. Record the connection ID, revision, issuer, subject and client ID. Credentials are never passed to the MCP adapter.
2. In the exact Auth0 tenant identified by issuer, use the Auth0 Management API or Auth0 Dashboard to enumerate **all** user grants, including every page, and select only those for the queued subject and client. Delete every matching grant; this also revokes its associated refresh tokens. Verify the user/client grants and refresh credentials are gone. If using Management API, use a separate short-lived operator token with `read:grants`, `delete:grants` and the required refresh-token inspection/revocation permissions. Do not use a different application's `/oauth/revoke` credentials; that endpoint may return success without revoking this client's token.
3. Keep the connection pending if any remote operation fails or cannot be verified. Retry from step 1; deletion and inspection can be repeated. Record tenant, subject/client, deleted grant IDs, refresh-token verification and timestamp in the restricted operator audit system.
4. Run `node apps/api-server/scripts/mcp-revocations.mjs confirm CONNECTION_ID REVISION 'Audit ticket and verified revocation evidence'`. The server records evidence and only accepts the current pending revision. The connection stays disabled. Never confirm based solely on the user's disconnect request or a successful local HTTP response.
5. The user may explicitly reconnect through the normal authenticated dashboard endpoint. That is fresh user approval to restore this existing connection, including its name and assignments. Existing signed access JWTs may remain cryptographically valid until expiry and can work again after this explicit approval; reconnect does not promise new token issuance. Require a fresh authorization flow operationally if old JWT access is unacceptable.

Do not stop at local disconnect: pending rows are operational work requiring an administrator. Monitor queue age and assign an on-call owner. General API authentication and IsAdmin protect both queue and confirmation; MCP tokens cannot use them. Live Auth0 tenant behavior and permissions must be acceptance-tested by operators before enabling production access.

References: [Auth0 grant deletion and refresh revocation](https://support.auth0.com/center/s/article/Refresh-token-revocation), [issuing-client requirement](https://support.auth0.com/center/s/article/A-Refresh-Token-Must-Be-Revoked-by-Its-Issuing-Client).
